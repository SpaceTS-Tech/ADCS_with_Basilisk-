# Integrated ADCS Model (`v1`)

## Purpose

This folder is the model-in-the-loop development area for the Attitude
Determination and Control System (ADCS). It combines the spacecraft plant
dynamics with the ADCS software so that control algorithms, mode transitions,
and actuator commands can be tested before generating flight-software C code.

Changes should normally be developed and validated here first. After the
integrated tests pass, the software changes can be transferred to the
software-only model in `../FlightSW_testing/`.

## Main files

| File | Purpose |
| --- | --- |
| `ADCS_v1.slx` | Main integrated Simulink model containing the plant and ADCS software. |
| `ADCS_FSM_v1.slx` | ADCS finite-state-machine model. |
| `ADCS_FSM_test.slx` | Root-I/O harness used by the automated FSM test suite. |
| `ADCS_FSM_v1_test.slx` | FSM test model that includes the dynamics-related setup. |
| `ADCS_pointing_test.slx` | Harness for testing pointing behavior. |
| `ADCS_Software_test.slx` | Harness for testing the ADCS software subsystem. |
| `sid_test.slx` | Additional simulation/test model retained for development. |
| `parameters.m` | Initializes simulation timing, initial conditions, references, gains, actuator limits, and test inputs. |
| `satellite_params.m` | Returns a structure containing spacecraft inertia, mass, thruster, controller, and timing parameters. |
| `run_ADCS_FSM_test_suite.m` | Runs automated root-I/O FSM cases and writes the Excel test report. |
| `individual_test.m` | Runs one FSM root-I/O test case against `ADCS_FSM_test.slx`. |
| `individual_test_with_dynamics.m` | Runs one test case against `ADCS_FSM_v1_test.slx` after loading the plant parameters. |
| `build_adcs_fsm.m` | Programmatically creates a new structural `ADCS_FSM.slx` model. It will not overwrite an existing file. |
| `ADCS_FSM_test_Report.xlsx` | Generated FSM test results. |

Files with the `.slxc` extension and the `slprj/` directory are Simulink cache
or build artifacts. They can be regenerated by MATLAB/Simulink and should not
be treated as the source of the design.

The `Data Sheet/` directory contains design descriptions, control-algorithm
documentation, and FSM test-case documentation.

## Requirements

- MATLAB
- Simulink
- Stateflow
- Any additional MathWorks products required by blocks used in the models

Use a MATLAB release compatible with the checked-in `.slx` files. Before
saving a model in a newer release, confirm that the team no longer needs to
open it in an older release.

## Running the integrated model

Start MATLAB, change to this folder, initialize the parameters, and open the
main model:

```matlab
cd('path/to/ADCS_Software_Simulink/v1')
parameters
open_system('ADCS_v1')
```

The model can then be run from the Simulink toolbar or from MATLAB:

```matlab
out = sim('ADCS_v1');
```

Review the logged attitude states, angular rates, controller modes, and
actuator commands. The exact logged variables depend on the current model
configuration.

## Configuration data

`parameters.m` defines the working simulation configuration, including:

- Base sample time (`ts`)
- Initial attitude quaternion and angular rate
- Reference attitude and angular rate
- Detumble, pointing, hold, slew, spin, and desaturation gains
- Reaction-wheel inertia and momentum limit
- Mission-command and mode-manager input values

`satellite_params.m` contains the plant-oriented parameters, including:

- Spacecraft inertia matrix and uncertainty terms
- Dry mass, initial fuel mass, and specific impulse
- ACS thruster force, moment arm, minimum impulse bit, and timing
- Controller gains and Schmitt-trigger thresholds
- Actuator/simulation timing data

Keep units consistent with the comments in these files and with the receiving
Simulink blocks. If a parameter is changed for a test, record the change with
the test result.

## Automated FSM testing

Run the test suite from this folder:

```matlab
run_ADCS_FSM_test_suite
```

The script:

1. Opens `ADCS_FSM_test.slx`.
2. Checks the expected root input and output port names and order.
3. Runs the executable root-I/O test cases.
4. Compares actual and expected outputs.
5. Writes `ADCS_FSM_test_Report.xlsx`.
6. Marks failed or errored cases in the report.

The expected root inputs are:

1. `mission_cmd`
2. `gps_valid`
3. `tle_error_high`
4. `ads_fine_allowed`
5. `ads_fault`
6. `detumbled`
7. `reference_available`
8. `energy_low`
9. `recovery_ready`
10. `wheels_saturated`
11. `desaturated`
12. `spin_feasible`
13. `spin_axis_available`
14. `optical_target_available`
15. `sun_sensor_valid`
16. `intersat_sensor_tracking`

The expected outputs are:

1. `actual_ephem`
2. `actual_ads`
3. `actual_frame`
4. `actual_acs`
5. `actual_mtq_enable`
6. `actual_rw_enable`
7. `actual_thruster_enable`
8. `mode_degraded`

If a root port is renamed, reordered, added, or removed, update both the
harness and `run_ADCS_FSM_test_suite.m`. A port-order mismatch is reported as a
preflight error rather than silently testing the wrong signals.

## Running an individual FSM case

Edit the `input` vector in `individual_test.m`, then run:

```matlab
individual_test
```

The first input is converted to `uint8`; the remaining inputs are Boolean. The
script simulates for 10 seconds and displays the final eight output values.

For the dynamics-aware harness, edit and run:

```matlab
individual_test_with_dynamics
```

This script loads `parameters.m` and `satellite_params.m` before running
`ADCS_FSM_v1_test.slx`.

## Regenerating the structural FSM model

`build_adcs_fsm.m` creates `ADCS_FSM.slx` with a fixed-step discrete solver and
a 0.1-second step. It is a model generator, not an in-place updater.

Run it only when a new generated model is desired:

```matlab
build_adcs_fsm
```

The script intentionally stops if `ADCS_FSM.slx` already exists. Review and
compare the generated model before using it to replace or update a versioned
model.

## Recommended development sequence

1. Update parameters or ADCS logic.
2. Run the relevant focused harness.
3. Run `run_ADCS_FSM_test_suite`.
4. Run the integrated `ADCS_v1.slx` scenario.
5. Review modes, state histories, actuator commands, limits, and test reports.
6. Transfer the verified software changes to `../FlightSW_testing/`.

Do not copy the plant dynamics into the flight-software model. The
software-only model must retain a clear boundary between environmental/vehicle
inputs and ADCS outputs.
